# SearchAd completion design — software completion with explicit operational blockers

Date: 2026-10-05 KST. Baseline: `0c2b4a1fe20c243c19e2cfd8e97d500fa833061f`, existing Draft PR #28. This design covers issues #18, #19, #20, remaining software acceptance in #21, and a formal disposition of the unresolved #26 boundary. It does not authorize #22.

## Authority and completion definition

Read together with `smartstore-bridge/docs/NAVER_SEARCHAD_FULL_IMPLEMENTATION_PLAN_V2_1.md`, `NAVER_SEARCHAD_FULL_INTEGRATION_DESIGN_V1_1.md`, `SEARCHAD_RECOVERY_DASHBOARD.md`, and current issue bodies/comments. Current dashboard and October 5 checkpoints supersede historical progress and permissive September sketches. Existing migrations and public lifecycle behavior are the compatibility baseline; old local checkpoint counts are not evidence of current implementation.

Software complete means production composition, HTTP authorization, role OpenAPI, deterministic services, durable PostgreSQL state, restart behavior, and offline upstream fixtures are implemented and verified for the supported contracts below. It does not mean live HAAR capability, operational activation, every raw operation executable, or trustworthy all-writer remote absence. Keep #26 open for its unresolved requirement, or formally split it only through an authorized tracking action. No claim that the whole project including #22 has shipped.

Global invariants:

- Node.js >=22.5.0; ES modules; node:test; PostgreSQL 16 acceptance.
- Preserve migrations 0001–0009 byte-for-byte; only append 0010–0013.
- No live Naver request, production DB/config/gate change, deployment, main/base merge, or merge of PR #28.
- Default automation mode is `observe`; new report registration and worker gates default OFF.
- Reuse change plan → one-time approval → execution → verification/reconcile; no second execution engine.
- Parent campaign/adgroup deletion remains disabled and absent from public routes/OpenAPI.
- Empty inventory, stale evidence, missing values and unknown outcomes never become positive authority.
- Every authority-bearing value is server-derived and bound to Customer, entity, current spec SHA, credential fingerprint, upstream origin, collection time and source record.
- Raw execution tokens, credentials, temporary report URLs/authtokens and customer PII never enter persisted request/result/audit payloads or logs.
- Read-only recovery never issues Canary PASS, restores a consumed token, refunds unknown risk, or blindly replays POST/DELETE.

## Architecture and application ownership

Add focused modules under `smartstore-bridge/src/naver/searchad/{reporting,circuit,automation,worker,validation,profitability}`. Reuse gateway/credentials, existing activation and account-row send fence, catalog identities, existing write services, HTTP role/Customer checks and PostgreSQL migrator.

A new `bootstrapSearchAdCompletionRuntime({app,env,clock,blobStorage,logger})` composes reporting, Circuit, automation, profitability and validation services. `bootstrapV05` receives optional deterministic `clock` and explicit storage injection, constructs this runtime after activation/hierarchy and catalog setup, and publishes `app.searchAdCompletionRuntime`. The existing lazy write runtime receives the completion Circuit guard and is resolved through one shared accessor, never a second privately instantiated writer. Standalone worker uses the same application/service factory and a headless resource disposer, not an HTTP listener.

Every subsystem task includes its routes and its role OpenAPI entries. Disabled modules return a sanitized 503; public readiness says required/initialized/ready only, not account authorization. `close()` is idempotent, drains or abandons leases safely and closes only owned pools/storage. Restart tests reconstruct bootstrap and HTTP, not merely repository objects.

Common runtime types (JSDoc, not a TypeScript migration):

- `Clock = () => number` (epoch milliseconds); all policy decisions use the injected clock. SQL receives the same timestamp for business checks. DB lock timeout is wall-clock infrastructure, not policy time.
- `Scope = {customerId:string, principal:AuthenticatedPrincipal, requestId:string}`. Worker principals come from server configuration and Customer allowlists, not job payloads.
- `Identity = {customerId,specSha,credentialFingerprint,upstreamBaseUrl}`; immutable observations add `entityType`, `entityId`, `observedAt`, `sourceRequestId`, canonical response SHA and explicit KST range.
- Money persists as PostgreSQL numeric/decimal strings; arithmetic uses exact scaled integers. API returns decimal strings or null, currency and basis. Never silently round floating-point evidence or treat null as zero.

## Reporting

### Observation and registration

`StatsObservationService.collect({customerId,entityType,entityId,since,until},context)` uses the pinned single-entity `/stats` operation, `fields=[salesAmt,impCnt,clkCnt,ccnt,convAmt]`, explicit valid KST dates and `allDays`. Reject datePreset, arbitrary fields, supplied spend/cycle/identity/evidence and unsupported entity kinds. The server validates exactly one returned entity, the documented allDays response shape, strict numeric values, valid KST `cycleBaseTm`, and identity both before and after I/O. Because the pinned SummaryStatResponse does not document a range echo, scope binds the exact server-owned KST request range and canonical response hash (`rangeBasis=server_request`); optional echoed dateStart/dateEnd must both match exactly (`rangeBasis=response_echo`). Required salesAmt/impCnt/clkCnt/ccnt cannot be missing. The requested but undocumented SummaryStatMap convAmt is optional: absence persists null and missingMetrics=[convAmt], while a provided value requires strict finite exact decimal validation. Missing/empty response is not zero. `/stats.salesAmt` means VAT-included advertising cost, not commerce revenue. SummaryStatMap verifies only the returned id, not the entity kind; observations expose entityTypeBasis=server_request and cannot independently establish remote entity type. Future trusted selectors must confirm type against a server-owned verified mapping, pinned entity GET or master evidence before using stats for automatic decisions. These are near-real-time observations, never stabilized spend proof by themselves.

`ReportJobService.register({customerId,kind,reportType,statDate?,fromTime?,intentKey},context)` persists the canonical intent before exactly one locally authorized registration attempt. `kind` is stat/master; report type/item comes from the pinned registry/lifecycle rules. Same Customer+kind+key and hash returns the same intent; another hash is 409. Only the current acknowledged fresh INSERT winner receives a single-use opaque in-memory dispatch permit; existing intents, including planned rows after a crash or ambiguous claim, never reconstruct dispatch authority. Consume that permit before any claim await. Atomic planned→dispatching CAS plus committed acknowledgement is required before transport. An ambiguous COMMIT or network result becomes unknown/manual review and can never reopen dispatch. Claim COMMIT loss remains non-dispatchable even if PostgreSQL actually rolled back and diagnostic quarantine writes fail. Creation acknowledgment loss is before dispatch: an existing intent is returned without a permit; an absent intent can be freshly created because no claim/send occurred. A crash after fresh creation or between committed claim and fetch may mean zero remote calls; this design promises at-most-one local attempt, not remote exactly-once.

Stat `updateTm` is recently modified time, not exact generation evidence: retain it only as `remoteUpdatedAt` in sanitized metadata and leave stat `reportCreatedAt` null. Master `updateTime` is explicitly documented generation time. Persist server-clock local registration attempt start (a conservative pre-fence bound, not delivery proof), actual transport implementation entry under the authoritative account fence (local initiation, not remote delivery proof), registration acknowledgment and first observed BUILT timestamps separately. A fresh owned registration and BUILT observation can describe a derived generation window. R13 uses attempt start minus configured finite clock uncertainty through download completion plus uncertainty, with monotonic attempt/initiation/acknowledgment/BUILT ordering. This assumes a fresh acknowledged owned job causally generates its report; configured uncertainty is declared, not measured synchronization. Date-only notices use KST and separate finite rollout uncertainty. A schema requires the entire widened window strictly on one side of a boundary. Only its lower bound establishes D+3/48h age, and successful D+1, D+2 and D+3 slots are mandatory. Identical archived bytes retain their original binding; changed bytes revoke prior selection and only a later proven generation can explicitly restabilize. Missing policy quarantines; later ingestion must label that basis and quarantine schema-boundary crossings or unowned legacy jobs rather than invent an exact stat generation timestamp.

`SearchAdOperationGateway.executeReportJob(operationKey,input)` admits only the two pinned report-registration POST keys with its separate `allowReportingJobs=false` gate, normal Customer/spec/tier/allowlist checks and retrySafe=false. It must not mutate the generic gateway configuration to enable advertising writes. Registration uses the authoritative account fence; no caller URL or operation override. `ReportJobService.poll/reconcile({customerId,reportJobId},context)` resolves only a persisted response-returned remote ID. If POST lost the ID, GET lists may produce sanitized diagnostic candidates but cannot establish ownership by unique type/date/time match, even when exactly one candidate exists. Unknown ID remains manual_review. `/master-reports` listing is capped at 100 recent jobs in the pinned Swagger and is not complete absence proof.

Processing states are `planned`, `dispatching`, `registered`, `polling`, `built`, `ingesting`, `ingested`, `unknown_outcome`, `manual_review`, `failed`. Data quality is a separate field: `provisional`, `stabilized_by_policy`, `changed_after_generation`, `quarantined`, `failed`.

### Signed download, storage and schema

`ReportDownloadAdapter.download({customerId,reportJobId},context)` obtains a fresh canonical download URL from a GET of the bound remote job and retains it only in memory. It validates exact HTTPS origin `https://api.searchad.naver.com`, exact `/report-download`, no credentials/fragment/alternate port/encoded path bypass, known single auth token parameter and optional case-preserved fileversion parameter; unknown or duplicate credential parameters fail closed. Preserve the upstream query values/casing rather than reconstructing a guessed token URL. HMAC signs `GET./report-download` under the existing timestamp.method.path convention. Disable redirects and impose response timeout and a configured maximum body size (default 64 MiB, streamed). Abort oversized/truncated/inconsistent responses. Never store/log the URL or its digest as usable credentials. Public download endpoint serves already archived bytes through the application or safe metadata, never the remote URL.

This transport operation is sample/notice-backed and absent from the 126 raw Swagger operations. Model it as a separately documented internal transport capability, not a forged 127th raw operation or generic arbitrary-URL exception.

`ReportBlobStorage.put({customerId,sha256,bytes,contentType,retainUntil}) -> {key,sha256,size}` and `get({customerId,key}) -> bytes` have deterministic Customer-prefixed content-addressed keys and verify SHA on both directions. Supply `LocalReportStorage` for tests/development and `S3CompatibleReportStorage` through an explicitly configured SDK client for durable production composition; missing durable storage makes required production ingestion unready. No local production fallback. Persist blob before ingestion commits; DB failure leaves a harmless unreachable blob, not falsely ingested state. Optional Google Drive archive is secondary and cannot turn failed primary storage into success. Raw reports/snapshots retain two years; audit three years; no destructive retention purge is activated in this work.

Registry selection binds `(kind,reportType,reportCreatedAtKst,statDate,parserVersion,orderedSchemaSha)`. The exact ordered columns and types come from pinned official documents, not arbitrary caller mapping. Headerless reports require a verified ordered schema; matching column count alone is insufficient. Parse TSV including CRLF/BOM/empty trailing columns; reject malformed encodings, impossible dates, overflow, Customer/entity mismatch, duplicate conflicting natural rows and unexpected columns. Stage first; atomically promote all validated rows and ingestion metadata; quarantine preserves original bytes/reasons and cannot create trusted spend evidence. Deduplicate generation and natural metric dimensions so recollection replaces the selected generation, never adds the same day's spend again.

Support AD performance, AD_CONVERSION, EXPKEYWORD and master Campaign/Adgroup/Keyword/Ad as functioning exact-schema formats, plus ADEXTENSION/ADEXTENSION_CONVERSION boundary schemas. The pinned official `assets/i18n/markdown-en-US.json` contains the StatReport ordered tables; the official MasterReport documentation embeds gist `naver-searchad/186ca42e1e8596b0e3dcf74e3a86c04f`, whose revision/hash must be pinned. Preserve exact documented enum mappings, including SearchKeywordType5=exact where the source table specifies it. An all-unsupported parser registry is not functional completion. Support other known performance, conversion, search-term and master formats through explicit descriptors. Any descriptor whose full official ordered schema is unavailable is registered as unsupported/quarantined; it cannot be guessed merely to increase coverage.

Required lifecycle boundaries:

| Boundary (KST) | Required behavior |
| --- | --- |
| 2025-04-09 / 2025-05-09 | NAVERPAY_CONVERSION has no new data, then no historical access; new jobs/download denied. |
| 2025-07-01 | Search-term aggregation/type mapping changes by statDate; preserve unknown enum rather than guess. |
| 2025-10-19 / 2025-10-27 | Master/stat fileVersion query introduced; preserve returned value/case. |
| 2026-03-30 | By statDate, COST becomes rounded long and VAT-included; preboundary historical data remains unchanged even when regenerated. Preserve its historical basis; never apply the new normalization retroactively. |
| 2026-07-16 | Adgroup master AI Ads column; no corresponding write authority. |
| 2026-11-16 | ADEXTENSION 15→14 and ADEXTENSION_CONVERSION 14→13, chosen by report generation time even for historical statDate. |

A D+1/D+2/D+3 recollection series is keyed by Customer, type and KST statDate. Only a complete exact-schema D+3-or-later generation at least 48 hours after that KST day's end, with valid identity and policy provenance, may produce `stabilized_by_policy`. This is revocable policy stability, not upstream immutability. Changed later generation appends `changed_after_generation`, invalidates dependent current evidence and blocks automatic increases until restabilized. Missing collection and partial aggregates remain untrusted. VAT values preserve raw/basis/gross/net/policy-version independently.

## Circuit and durable outcome projection

`CircuitService.evaluate({customerId,entityType?,entityId?,ruleId?,actionClass,incrementalSpendKrw},context)` loads current policy, trusted evidence, unresolved reservations and durable mutation outcomes. Defaults: entity cooldown 24h; manual-change hold 24h; incremental spend 30000 KRW; daily loss 50000 KRW; consecutive failures 3; unknown outcomes 3; post-change observation 24h; spike multiplier 2.0. Explicit Customer daily spend ceiling is required before automatic execution; absent baseline cannot satisfy a deviation check.

Failure ceiling pauses that rule; unknown ceiling pauses all ordinary Customer writes; realized loss/incremental ceiling blocks increases; spend spike pauses automation; detected manual drift places entity hold. Sticky manual pause is never cleared by successful collection, midnight rollover or restart. Admin pause/resume requires current explicit Customer scope and reason; resume does not erase unresolved outcomes or override account suspension. Read/reconcile remain available; rollback is exempt from Circuit pause only, still subject to its existing gate, identity, after-hash and account fence.

Use durable existing `searchad_write_attempts` and lifecycle/canary event/intent sources as the recoverable outcome source. Project idempotently by `(sourceKind,sourceId)` with per-source cursors and immutable Circuit events. Projection exceptions are outside the primary mutation transaction/result path: never report a remote applied mutation as failed only because Circuit bookkeeping failed. Before another ordinary mutation, unprojected or unreadable outcomes and unresolved in-flight intents deny dispatch until projection catches up. This requires real production hooks and final send checks, not only wrapping automation calls.

Extend the account fence's internal dispatch context and pre-send callback, preserving account-row ordering and the final synchronous validate→fetch initiation. Circuit dispatch authorization is checked using that same locked account store. Request purpose/class is constructed by trusted gateway adapters (`ordinary`, `lifecycle`, `canary`, `rollback`, `report_registration`); public input cannot choose bypass classes. Unknown/consumed reservations cannot be recycled. This remains a local initiation guarantee, not physical delivery or external writer exclusion.

## Automation and worker

Automation modes: observe records decisions only; recommend records actionable proposals; approve creates a server-owned change plan and uses the existing explicit Executor approval/execute path; limited auto additionally requires a server-admin policy delegation and verified eligibility. `AutomationService.evaluate({customerId,policyId,slotAt?},context)` accepts no evidence objects/IDs, approval objects, remote overrides or supplied current values. Repository selects latest trusted evidence for exact Customer+entity+current identity and freshness. Deterministic decision keys hash policy revision, scope, selected input hashes and logical slot; same key cannot create another plan.

Durable reservations precede plan/token dispatch. Raw approval tokens exist only transiently; a restart after token issuance without acknowledged execution goes to reconcile/manual review, not token regeneration. `AutomationService.prepare` creates only known server recipes; `executeApproved` delegates the exact existing plan ID to `ProductionSearchAdExecutionService.execute`. Human and policy actors are separately audited; policy delegation never substitutes for activation evidence.

Worker is a separate `npm run searchad:worker` process. `PostgresWorkerRepository.claim({workerId,now,leaseMs})` uses `FOR UPDATE SKIP LOCKED`, increments lease generation and returns an opaque owner token. Heartbeat/finish are CAS by job+owner+generation; an expired old owner cannot finish or mutate. Job history survives restart. Unique `(customer_id,schedule_id,slot_at)` and canonical payload hash prevent duplicate schedule intents. UTC storage and explicit Asia/Seoul daily report calendar avoid timezone drift. Default stats interval 15m, evaluation 1h, report recollection 03:00 KST for D+1/D+2/D+3; stale stats/evaluation backlog >1 interval is recorded skipped, report backfill is capped to seven days and older slots are recorded skipped. No catch-up mutation burst.

Handlers invoke only reporting/automation services. Claim expiration does not grant resend authority: pure collection can retry boundedly; registration uses the same durable report intent; automation execution inspects the same run/plan and reconciles consumed/unknown outcomes. Worker checks lease just before service dispatch; downstream service claims still enforce one attempt if a worker pauses after that check. Schedule payload is exact allowlisted configuration, not an authority envelope. Enabled worker without PostgreSQL fails startup; CI cannot silently skip lease tests.

## HAAR profitability and recommendations

`ProductEvidenceService.collect({customerId,haarProductId,since,until},context)` resolves verified Customer-channel binding and canonical HAAR→channel→SearchAd mapping; it reads existing server-side product/import snapshots and calls configured read-only Commerce providers for stock, sale state, order line, cancellation/return and settlement observations. Provider methods are `collectProductState`, `collectOrderLines`, `collectAdjustments`, `collectSettlements`; the application creates actual adapters from existing Commerce gateway/Cafe24 client, not HTTP-supplied functions. Provider capability and missing endpoint/permission are explicit statuses. At least actual configured SmartStore product/order/adjustment and Cafe24 product/variant read paths must be wired and exercised; all-provider-unavailable or fixtures-only composition is incomplete. Implement settlement reads when pinned descriptors and official fields establish them. A connector without verified settlement or cost semantics yields missing/partial evidence, never zero cost or synthetic actual profit.

Customer-admin may enter effective-dated cost inputs with source/reason for a canonical HAAR product/variant. These are labeled manual/estimated inputs, not fabricated upstream evidence or activation authority. Source costs resolve through current effective HAAR source/variant links; no QueenSilver-specific assumption. Store only relevant numeric/date/product identifiers and hashed source references; never customer address, buyer name, phone, payment credentials or raw order payloads.

N:M ad mappings are immutable revisions with validity, method, confidence and allocation basis. Exact/manual verified ID chains can be confidence 1.00; >=0.90 is merely an automation candidate; 0.70–0.89 analysis only; <0.70 unresolved. Aggregate adgroup/campaign spend cannot be assigned in full to every linked product. Shared spend requires explicit verified weights summing exactly to 1 for the generation, or remains unallocated/partial. Deduplicate order-line and adjustment identities; cancellation/returns already reflected in net revenue must not be subtracted twice.

`calculateProfitability(inputs,policy) -> ProfitabilitySnapshot` returns attributed ad revenue separately from commerce paid/net revenue, raw/normalized ad cost, COGS, fees, shipping, seller discounts, outstanding return provision, gross margin, contribution, margin rate, break-even ROAS, profit ROAS, ROAS/ACoS/CPA/CVR, quality and missing-component reasons. Contribution = net revenue − COGS − fees − shipping − seller discounts not already netted − outstanding cancellation/return provision − ad cost. Define all ratio numerator/denominator/basis in the snapshot; undefined/zero denominator yields null, not Infinity. `actual` requires complete reconciled settlement/cost/allocation evidence; `estimated` requires explicitly estimated components; `partial` has some usable actual inputs and missing components; `unknown` lacks minimum sales/cost scope. Missing essential costs yield null contribution rather than fictitious positive profit. Freshness and provenance are exposed alongside values.

`RecommendationService.generate({customerId,haarProductId,since,until},context)` stores deterministic keyword/search-term, bid-estimate, budget and negative/stop proposals with input hashes, reasons, confidence, applicable validator/operation/capability and an executable flag. Read-only keyword/estimate gateways are used only with supported pinned descriptors. Unsupported negative-keyword/create/bid mutation mapping remains a recommendation with explicit blocked reason. Sparse conversions (<3), stale data, unallocated spend, partial profit and uncertain mappings cannot produce profit-based increase proposals.

Limited auto v1 can execute only currently mapped campaign `dailyBudget` and `userLock` recipes under existing exact activation fields. Allow stopped/lock-on and bounded budget adjustment; unlocking/relaunch, bid changes, keyword creation and delete remain manual/blocked until separate exact authority exists. Require seven complete KST observation days, fresh stock/sales evidence <=15m for inventory-based decisions, current near-real-time stats <=30m, stabilized spend/profit generation <=24h, mapping >=0.90, explicit policy delegation, fresh valid activation, Circuit approval and per-entity lock. Max change 20%, max daily budget 100000 KRW, max incremental spend 30000 KRW, max daily operations 200; tighter Customer policy wins. Increases require actual profitability and >=3 conversions plus verified estimate/balance evidence; otherwise decline with reason. Seven elapsed calendar days or seven fabricated rows alone are insufficient. All automation must obtain post-change outcome verification; failure stays unknown/manual review with no next execution. Rollback/reconcile reuse the existing service paths.

## HTTP and documentation contract

All routes are under `/api/v1/searchad`, require explicit Customer scope, exact request schemas and authenticated principal attribution. Resource lookup checks Customer before returning 404/403 without cross-scope metadata.

| Surface | Minimum role |
| --- | --- |
| GET reporting observations/jobs/:id/metrics; profitability/products/:haarProductId; recommendations; circuit; automation/policies/runs; validation/operations | Reader |
| POST reporting/stats; reporting/jobs; reporting/jobs/:id/poll or /ingest or /reconcile; product-evidence/collect; recommendations/generate; automation/evaluate; automation/runs/:id/prepare | Operator |
| Existing changes/:planId/approve and /execute; automation/runs/:id/execute-approved | Executor |
| POST circuit/pause or /resume; automation/policies; worker/schedules; product-mappings; product-costs; customer-channel-bindings | Admin |
| GET worker/jobs and worker/schedules | Admin |

Reporting POSTs perform server-controlled collection/registration only; ad writes cannot be smuggled into them. Registration additionally requires the dedicated report gate; automated dispatch additionally requires worker/automation gates. Role documents use `/openapi-searchad-completion-{reader,operator,executor,admin}.json`, and existing system documentation links them. Validation registry and blocker status are descriptive only, never activation/promote endpoints.

## Validation registry, scanning and acceptance

Exactly 126 unique pinned operation keys are classified as `implemented_canary_proven_family`, `implemented_manual_only`, `public_unverified`, or `internal_or_quarantined`. Each record includes implementation/test references, exact scope and `liveVerified:false` unless independently existing real evidence supports otherwise. Canary-proven family describes the bounded code family, not every field/Customer or synthetic live proof. The registry is immutable read-only descriptive data; it cannot modify runtime allowlists or issue evidence. Separate signed download capability does not alter the 126 count.

Expanded scanner enumerates all execution source directories, HTTP route entrypoints and transport imports, not a hardcoded 16-file subset. Parse code/imports to reject fetch aliases, global fetch, http/https/undici/axios/WebSocket/raw client initiation in service layers. Explicit narrow reviewed transport boundaries are reported separately; adapters delegating to those boundaries are not falsely described as raw network calls. Add mutation controls that introduce a forbidden direct call and show scanner failure. Keep existing boundary tests and dynamic outbound network traps: static zero is not a security proof.

Offline contract tests inject clock, credential fixture and a closed fake upstream; real PostgreSQL tests run isolated schemas, competing connections, COMMIT ambiguity, restart and authorization paths. Local missing `TEST_DATABASE_URL` may skip only explicitly optional integration files; CI asserts the variable, DB reachability and zero skipped tests. Clean CI applies exact migration filenames/checksums 0001 through latest before any test populates public schema, immediately repeats with `applied:[]`, and retains prior migration assertions. Full tests, syntax, diff/secret scanner, operation coverage and production dependency audit must use fresh results pinned to commit SHA. Network-blocked audit is unverified, not zero vulnerabilities.

## #26 hard boundary

No available pinned list contract proves snapshot-complete absence across unmanaged descendants and independent external writers, and no available local lock excludes those writers. Master inventory, repeated empty scans, exact local owned IDs and an Admin flag are insufficient. Keep `completeAbsence:false`, `snapshotConsistency:'unproven'`, `cleanupAuthority:false` and public `cleanup:false`. Expose a sanitized read-only blocker reason; retain 404 for attempted public parent cleanup before and after restart. A future resolution requires authoritative upstream snapshot/conditional-delete semantics or a separately established complete writer-exclusion contract plus independent review; neither exists in this implementation scope.

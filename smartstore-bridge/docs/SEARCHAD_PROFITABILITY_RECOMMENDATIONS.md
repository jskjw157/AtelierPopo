# Product profitability and recommendations (Task 9)

`ProfitabilityService.calculate({customerId, haarProductId, since, until}, context)` selects current configured provider bindings and effective canonical mapping revisions, exact-range commerce observations and current-identity selected report generations. The API accepts only that scope. Money, hashes, quality, provider accounts, allocation verification and executable status cannot be supplied through HTTP.

Operator `POST /api/v1/searchad/recommendations/generate` calculates and stores one deterministic immutable snapshot, then records six decisions: keyword, search-term, bid-estimate, budget, negative and stop. Reader `GET /api/v1/searchad/profitability/products/:haarProductId` returns the current scoped calculation and `persisted` status. Reader `GET /api/v1/searchad/recommendations?customerId=…&haarProductId=…&since=…&until=…` lists decisions only for the current input generation. A Reader preview writes nothing. Customer checks precede selection; changing a configured provider requires a matching current binding and an explicit new mapping. Old snapshots remain archived but cannot be selected under the new identity.

## Exact calculation and quality

All money is represented as decimal strings. Provider ingress and the persistence projection accept JavaScript numbers only when they are safe integers; fractional or unsafe numbers become missing before stringification. Exact decimal strings retain their original spelling in observation provenance. Component provenance retains raw decimal spelling separately from normalized values. Arithmetic uses integer ten-thousandths of KRW; ratio division rounds half away from zero to six decimal places. Ratios include explicit numerator and denominator names. Missing values and zero denominators return null. Contribution is net revenue minus COGS, fees, shipping, seller discounts, outstanding return provision and ad cost. Each deduction explicitly states whether it is already included in net revenue. The non-netted golden is 100000−30000−5000−3000−2000−1000−10000 = 49000.

Ad-attributed revenue remains separate from commerce paid and remaining net payment. Naver completed cancellations/returns are already reflected in remaining payment and quantity: their null financial adjustment is not deducted again. An explicit outstanding manual return provision is a different estimate and is deducted once. Settlement entries with unverified unique ledger identity are kept as partial provenance and cannot establish actual reconciliation.

The pure calculator can label fully reconciled synthetic fixtures `actual`, fully specified explicit estimates `estimated`, incomplete usable sales evidence `partial`, and missing sales scope `unknown`. Runtime mappings are currently manual and allocation is unverified; Naver settlement reconciliation and Cafe24 financial capabilities remain incomplete. Current configured providers therefore cannot yield actual profitability or automatic execution authority. Missing essential costs or allocated ad cost leave contribution null.

Manual cost inputs are explicitly per remaining unit estimates. Only one product-level revision covering the entire requested KST sales interval can be applied. COGS may use one unambiguous KRW supplier-cost revision with the same interval coverage. Multiple suppliers, overlapping variants, a variant-specific cost without an order-line variant assignment, and partially effective intervals remain descriptive and unresolved. Costs are never summed across potential suppliers or all variants as if every source fulfilled each order. Selection retains all revisions intersecting the requested KST interval, including revisions that expired before calculation and excluding replacements that start after sales. Explicitly overlapping intervals stay ambiguous; a newer revision does not silently close an older open interval. Supplier costs also require the HAAR source link, and any variant link, to cover the sales interval. Undated links use their creation time as the conservative effective start; a newly created link cannot retroactively attribute historical costs without an explicit earlier valid-from date. Link intervals and their date basis are included in provenance. A cost and its source/variant relationships must share an intersection with the sales interval before they count toward assignment ambiguity. Wholly earlier or later relationships remain descriptive provenance and do not suppress an otherwise applicable cost. Partially intersecting relationships still make assignment incomplete, and a sole inapplicable relationship still reports a missing-link interval reason. Current Customer/account/binding authorization is still checked independently at calculation time.

Commerce lines deduplicate by scoped source reference. Ads use exactly one selected ingestion per report kind/type/date, with unique source rows; multiple mappings or channels do not replicate spend. Shared spend needs verified, generation-bound weights totaling exactly one. The pure allocation function conserves every 1/10000 KRW unit using largest remainder and product-ID tie breaking. Production manual weights never satisfy verified allocation. Raw spend is shown once as unallocated and cannot create conversions or product profit. Missing spend remains null.

## Immutable provenance and decisions

HAAR UUID casing is canonicalized before source selection/hashing; equivalent HTTP UUID spellings share one snapshot and decision set. Snapshot IDs and source-set/input hashes cover Customer, canonical product, date interval, current SearchAd identity hash, provider identity/bindings, effective mappings/costs and selected observation/report IDs and content hashes, and the scoped catalog projection sorted by channel product ID. A catalog sync therefore creates a new deterministic source identity while preserving earlier immutable snapshots. A final current-scope check rejects a binding/mapping change during calculation. Both tables reuse frozen migration 0015 and its immutable triggers. Repeating the same source generation and decision produces the same IDs and does not append duplicate records. Conflicting persisted content with the same deterministic identity fails closed. Freshness changes produce different input hashes without overwriting history.

Every decision records rule version, input/tool hashes, proposed patch, reason, confidence, expiry, operation/validator/capability and activation constraints. Sparse conversions (<3), stale inputs, partial profit, unallocated spend and uncertain mapping prevent profit-based increases. A fully qualified synthetic actual fixture can propose a budget within the existing 20%/100000 KRW caps. All Task 9 records have `executable:false`, `liveVerified:false`, `outcomeVerified:false` and `TASK9_READ_ONLY`. A proposal is never outcome proof. This task exposes no execution or limited-Auto endpoint.

The keyword adapter only delegates the exact pinned `/keywordstool` GET with `sideEffect:false`, `destructive:false`, runtime allowlisting and the existing read/capability gates. Server catalog hints and a positive keyword response projection avoid arbitrary request/response storage. Descriptor drift or gate denial records an unavailable decision. The pinned estimate descriptors are POST, `sideEffect:true`, create-gated. `bidEstimate` records `ESTIMATE_READ_CAPABILITY_UNAVAILABLE` with zero dispatches; it does not relabel those operations as read-only. Unsupported keyword, bid and negative mutation mappings remain non-executable proposals.

Automation still selects its existing current stats and stabilized spend. Task 9 additionally reports mapped canonical product IDs and `PROFITABILITY_EXECUTION_SELECTION_UNAVAILABLE`, with no profitability execution grant. Task 10 must establish its exact eligibility window through the existing plan/approval/execute/verify protocol.

## Validation

The focused suites are `searchad-profitability.test.js`, `searchad-recommendations.test.js`, and `postgres-searchad-profitability.integration.test.js`. PostgreSQL tests use isolated schemas, real migrations/runtime/HTTP and closed synthetic upstream traps. They cover immutable persistence, restart, role/Customer denial, serializable HTTP authority injection, provider rebind/remap, repeated actual report ingestion, shared spend across two configured channels, supplier/variant ambiguity, historical cost and link intervals, provider numeric type handling, and catalog sync followed by regeneration/restart. These fixtures establish local behavior, not live upstream evidence.

The execution scanner now serializes BigInt literal constants when comparing alias-analysis iterations. All reviewed AST node/context/provenance records remain unchanged. A new mutation test checks that legitimate exact-money code scans successfully while a forbidden call in the same BigInt module is still detected.

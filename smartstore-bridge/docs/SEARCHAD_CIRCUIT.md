# SearchAd Circuit: production boundary and recovery

Circuit is composed with the application-owned PostgreSQL account store even when reporting is OFF. Automation remains OFF/observe. Reader status is `GET /api/v1/searchad/circuit?customerId=...`; Admin pause/resume requires the current exact Customer scope, HTTP write gate and nonempty reason. Resume clears only the sticky manual pause. It never clears unknown outcomes, reservations, account suspension, rule failure counts or entity holds. Status exposes `counterBasis: 'unresolved_logical_failure_upper_bound'`. The rule counter is a conservative upper bound: it counts unresolved failed/unknown logical mutations, because source timestamps and UUIDs do not prove causal initiation order. Unrelated success never resets late failures; exact linked verification resolves only its own contribution. There is no counter-reset endpoint. Known-failed ordinary plans currently lack supported reconcile, so their rule hold can remain permanent; this is an explicit limitation for review before automation is enabled. No future revision/reset mechanism is claimed as implemented.

## Local ordering

Primary ordinary, Canary and hierarchy writes that change outcome/hold state take the authoritative `searchad_canary_accounts` row lock first. The affected source selectors require one actual matching account row; a zero-row lock read rejects the source transaction even if an account is registered concurrently. No source helper creates or unsuspends an account. Missing-plan 404 and missing-Canary-run update null remain distinct from an existing source with no account. Hierarchy then retains its run/object ordering. Read-only recovery bookkeeping also takes that lock, without requiring the account to be unsuspended: recovery reads remain available.

Projection runs outside the primary mutation transaction and cannot replace its result/error. Each projection insert and manual control commits in its own account-first transaction. Before dispatch, projection catches up; the final account send fence then locks the account and, using that same SQL client, checks source anti-joins, primary unresolved state, policy, projected outcomes and selected evidence. Any newly committed source backlog denies the send. A source producer cannot commit while this fence holds the account lock.

The send fence always ROLLBACKs. It persists neither projection nor reservations. The internal pre-send callback may return a synchronous snapshot validator (or undefined). The fence rejects async/non-undefined validator results. It checks finite non-regressing clock, captured evidence expiry and exact KST day at initiation, then runs the existing synchronous identity check and immediately enters transport, with no await after either validator. The lock ends after initiation, before waiting for the remote response. This orders local initiation only; it is not physical delivery, remote exactly-once, or exclusion of external writers.

Report evidence producers take Customer advisory `report-circuit:<customerId>`, then the existing report/date advisory lock and job row. The final reporting selector takes that same Customer advisory lock after the account lock and retains it through initiation. Reporting producers do not acquire the account lock in the opposite order.

## Durable sources and canonical outcomes

| Source | Immutable projection identity | Logical mutation identity |
| --- | --- | --- |
| Ordinary write attempts | `write` + attempt UUID | owned plan UUID + execute/rollback |
| Canary events | `canary` + event UUID | owned run UUID + exact mutation phase |
| Hierarchy events | `hierarchy` + event UUID | explicit owned plan UUID; otherwise exact local object + lifecycle kind, with a separate read identity |

Ordinary rule association comes from the Customer-owned automation run linked to that exact plan; multiple ambiguous run associations fail closed. Neutral ordinary `plan/succeeded` audit is outside mutation-source enumeration. It can append without an account only while its existing plan remains locked in `planned` state. Actual planning/read services remain available; approval status updates and mutation outcomes require account presence, so approval can be locally unavailable until account registration. Previously projected planning rows positively linked to their primary plan-phase attempt are retained as audit but ignored for derived mutation outcome, observation time and counters; unlinked/orphan rows are not discarded. Every source row is retained once under `(Customer, sourceKind, sourceId)`. Cursors are informational, never timestamp watermarks; late, tied and backdated commits remain eligible. Hierarchy-mirrored ordinary plans are excluded from ordinary projection and hold queries because their exact plan-linked hierarchy events own the same mutation. They are not excluded from Circuit.

Neutral intent/remote acceptance cannot clear an unknown. Only a linked successful verification/reconciliation for that exact logical mutation resolves it. Linked verified success takes precedence over later-arriving duplicate uncertainty for the same one-shot mutation. Unlinked hierarchy GET recovery cannot establish the full mutation's success: its separate read identity leaves the original logical unknown counted. It may settle only the supported object hold. No GET reconstructs Canary PASS, a consumed token, unknown risk refund, an unknown remote ID, or a resend permit.

Active approved-and-consumed ordinary execution, hierarchy dispatching/delete-pending, pending exact Canary phase intents and unresolved automation reservations hold the Customer. Primary terminal state missing its required linked event also holds the Customer; mutable status alone is not proof of completion. Terminal unknown history holds its trustworthy target; absent trustworthy target falls back to a Customer hold. Hierarchy local object ownership can bind an unreturned sibling without inventing a remote ID. Thus a verified returned partial keyword leaf can use existing cleanup authority while one different terminal partial-batch unknown remains below the Customer ceiling of three. Pause, backlog, other active work, same-target holds and the unknown ceiling still apply; cleanup has no purpose exemption.

Canary `settleMutation` atomically commits run state and the exact phase-linked terminal event under the account lock. Baseline/read/spend events are neutral mutation evidence. Circuit projection follows independently. An uncertain primary commit cannot claim a durable verified result.

Ordinary rollback records an acknowledged account-first `rollback/send_intent` after the existing activation and exact after-hash checks, before transport. The primary repository refuses any existing rollback attempt for that plan, including across processes/restart. A pending marker holds subsequent ordinary dispatch until an exact rollback terminal event exists; prior execute success cannot settle it. A lost claim acknowledgement never sends and retains an in-process no-reentry hold plus best-effort primary quarantine. If the claim actually committed, its durable marker survives restart. Existing manual review/read recovery remains available; no new rollback replay/recovery authority is added.

## Storage and purpose boundaries

Production ordinary dispatch requires its primary repository to share the application's exact authoritative pool object. SQLite or an independently supplied pool retains reads/planning but cannot dispatch. Different pool objects may in fact address the same database; rejection is a conservative unsupported binding limitation, not proof of different physical databases. There is no cross-store mirror or configurable guard bypass.

Purpose, own plan/run/phase/object exclusion and before state come only from server-owned adapters and immutable internal context. HTTP fields cannot choose them. Reporting registration is a separate purpose. Rollback bypasses Circuit only, retaining account, activation, after-hash, claim and write gates. Supported stopped lifecycle/Canary creation is bound to the existing exact recipe and committed intent; a public `userLock:true` is not authority.

## Money, evidence and unsupported increases

Defaults are 24-hour entity cooldown, manual-change hold and post-change observation; 30000 KRW maximum incremental gross spend; 50000 KRW daily net loss; three rule failures; three Customer unknown outcomes; and a 2x spend spike. Automatic dispatch additionally requires an explicit Customer daily gross spend ceiling and comparable baseline. These remain unavailable by default.

Ordinary PUT classification accepts a proven dailyBudget/bidAmt reduction only when both values are nonnegative safe-integer KRW from the owned verified before state and request. Lock-on and unchanged nonmoney fields are non-increasing. DELETE is non-increasing. Missing prior, negative/fractional/overflow monetary values, batch payloads, unknown changed fields, unlock and ordinary POST remain increase-class and fail closed without evidence. A bid increase has no inferred daily spend bound. Scalar budget differences use exact safe-integer subtraction; there is no currency conversion or gross/net substitution.

Task 4 has no production net-loss provider: increase-class requests deny with `LOSS_EVIDENCE_UNAVAILABLE`. Gross report cost does not prove realized net loss. Task 9 owns genuine profitability-backed composition (Task 8 supplies upstream data). The internal optional selector is `lossEvidence.select({customerId},{client,now})` and must use the passed authoritative transaction plus its producer synchronization. Its result is `{customerId,statDateKst,amountNetKrw,quality:'actual',completeCustomerDay:true,identityVerified:true,observedAt}`. Identity must bind current Customer/spec/credential/upstream and underlying complete reconciled settlement, cost/allocation and policy provenance, not caller assertions. The returned final validator rechecks captured age/day at actual initiation; reporting spend selectors additionally return generation-bound `validUntil`. The service checks exact Customer/current KST day, nonnegative finite net amount, actual/complete/identity flags, no future observation and age at most 24 hours. Partial, estimated, unallocated or out-of-scope profitability cannot claim complete Customer daily loss. Task 9 must supply honest provenance; Task 10 cannot enable increases before that provider and a valid baseline exist.

## Verification boundaries

The HTTP SQLite helper is explicitly a component fixture with real plan/approval/execution services, signer/client, closed upstream and synthetic activation. It proves roles, Customer scope, token/master gates, verification, nonretry and HTTP queue/drain behavior, not native production authority. Actual supported shared-PG application positives, incompatible-store zero-send negatives, three production writer pause paths, primary projection failure, source commit ordering, canonical partial cleanup and rollback marker tests are native integration tests. Local skips do not accept these paths; PostgreSQL CI must execute them without skips.
